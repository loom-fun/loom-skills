## 1. Summary

The SDK supports published service ABI 1 and legacy HAL ownership. Preserve both in this
migration. The frozen DevLab sweep covered all 61 accepted production revisions. Both SDKs
produced identical diagnostics for each package. The manual Inkling R9700 card hits the same
six STRUCTURE/034 pure-effect diagnostics under both SDKs. Flash-Next's vision group hits the
same joint-link SYMBOL/013 collision on @qwen38.packet_capacity in both corpora. All 55
programs-only kit builds parsed on both SDKs. These are offline findings; runtime proof is
tied to individual cards and devices.

## 2. Breaking changes

| Surface | Old and new contracts | Migration and check |
|---|---|---|
| Text and sequence controller ABI | Published service version 1 retains its existing export signatures. Bare unversioned development exports now select ABI 2. | Keep the published service version and ABI. For an unversioned development controller, export each old role with a _v1 suffix and select version 1, or port the entire service to _v2. The ABI 2 publisher adds a proposal_counts buffer after progress and uses exact live token and span counts. Serve and exercise every changed service. |
| HAL ownership | Legacy hal.buffer, hal.fence and hal.file signatures remain accepted. The new contract borrows ptr handles and passes ownership with ref values. | Keep the legacy signature for existing packages. A port to explicit ownership must pair each owner's last use with a release and verify the linked service. |
| SDK pin | Previous packages pin 0.2.0 or another recorded SDK. The stable 0.3.0 wheel is available on PyPI. | Install in a separate root and verify its wheel hash. A staging package uses the new pin after its runtime sessions pass. |
| Speculative telemetry | ABI 1 may report proposed_tokens as null. Epoch capacity fields are replaced by scheduled_tokens. | Check telemetry consumers for nullable proposals and avoid deriving counts from configured draft depth. Verify tools and image endpoints on the runner. |

## 3. Mechanical steps

### 3a. An existing package

1. Install 0.3.0 with the installer from loom-setup.
2. Keep a copy of the published package revision and its SDK pin. Run the sweep on that
   package under both SDKs, then serve the same published preset with 0.3.0. Exercise text and
   tools, vision, or image generation according to its services.
3. After runtime validation, use sdk_pin.py stamp with the verified new SDK root on the
   staging copy's llm_config.json. Preserve the model, origin, program and tokenizer files.
   Use the explicit ABI migration in section 2 only for packages that use bare development exports.

### 3b. A manifest model

On DevLab, plan the Loom-only comparison by naming the migration branch, device and manifest
slug explicitly. The plan pins the accepted production package revision for the old measurements
and build inputs. The [accepted inventory](v0.2.0-to-v0.3.0-production.json) records all 61
slug and revision pairs. Report subsequent additions, deletions and changed heads as drift.
The final assembly reads metadata from that revision and uses the staging
head as the compare-and-swap upload parent.

~~~bash
python3 fleet/regen.py plan --base codex/sdk030-migration --device strix-halo \
  --mode sdk-loom --new-sdk 0.3.0 --state sdk030.json MODEL_SLUG
~~~

Run and collect the normal repeated sessions and gates. Confirm a row outside the band with
the planned same-runner ABBA job. Package publication requires the measured programs hash,
the verified 0.3.0 wheel for both performance variants, and a passing verdict. Then build the
card from the evidence and publish to staging. Preserve any verified existing baseline rows.

For cards outside the manifest, use the published-package procedure. Track image generation
and manually maintained packages independently from the decoder performance workflow.
Evaluate the Flash-Next and Qwen3.8-27B source uplift separately from ABI 1 compatibility.
[Library #127](https://github.com/ROCm/hrx-loom-library/pull/127) adds live token counts for
those upstream controllers. Match each published package's generator, quantization and
service variant to the upstream source before testing the change. The manually maintained
UD-Q4_K_XL package and AWQ-MXFP4 package need their own applicability checks.

## 4. Scripts

Use scripts/sweep.py for both SDK roots, fleet/regen.py for generated decoder cards and
loom-setup/scripts/sdk_pin.py to refresh a validated package's pin. Published ABI 1 does not
require a source rewrite.

## 5. Verification

Compare each package's parse/link diagnostics against the old SDK control. The fleet build
and static sweep cover compilation input and linking, while service ABI registration, device
loading, generation, and performance require separate DevLab sessions. Keep baseline and
new-run evidence tied to the exact production revisions and rendered staging package.

## 6. Behaviour changes to measure

Measure decode, prefill, long-context and four-stream rows for applicable decoder presets.
Inspect tool, image, speculative decoding and full-context admission behavior with the
registered services. Attribute changes to the runtime or package only after the comparison
controls for programs, preset, checkpoint and runner.

## 7. Simplifications available

ABI 1 compatibility removes the need for a fleet-wide code rewrite. Leave existing runtime
flags in place until a controlled measurement supports a change.

## 8. Opportunities

ABI 2 live work limits, explicit HAL ownership and checkpoint streaming can be evaluated in
separate measured changes.

## 9. Gotchas

- Same aggregate diagnostics on both wheels -> compare individual package and file findings before treating them as existing.
- A staging card has older provenance than production -> pin production for the comparison and assembly, then use the staging revision for the upload.
- A published input lists a data file as an object -> use its path when selecting Loom sources for the sweep.

## 10. Not applicable

The source-built libhrx API change and Bazel/C++ provider or loom_test BUILD migrations do not
alter the existing Loom source packages emitted by this repo.

## 11. Promotion

Keep uploads in loom-fun-staging until the owner approves production promotion. Preserve the
outgoing production revisions with their appropriate SDK tags before promotion. See the
[release checklist](../reference/release-checklist.md).
