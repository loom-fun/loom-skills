# Populate a Loom HF org

**Bundled paths ? first shell action.** Before running commands, set `LOOM_SKILL_DIR` in the shell to the
absolute directory containing **this** `SKILL.md`, using its path from the skill listing or read tool.
In Claude Code, run `export LOOM_SKILL_DIR="${CLAUDE_SKILL_DIR}"` (the host substitutes the path).
In Codex, Pi or another host, export `LOOM_SKILL_DIR` to the loaded file's directory. Use a
shell-compatible absolute path (Git Bash on Windows). Rebind before using another skill's commands
and in every new shell; it is not the working directory or SDK root. On Windows, use native `C:/...`
paths for file tools; `/c/...` paths belong to Git Bash. Never run an unresolved placeholder. Run bundled commands by quoted absolute path; do not run `scripts/...` from the working directory
or change into the installed skill tree. Install the complete Loom suite: sibling paths are required.

The job: make an org such as `huggingface.co/loom-fun` host one correct, fully assessed Loom package for each of the
top models that fit the device, every card generated by the current skill. This skill is the campaign around the
per-model skills. It orchestrates; the per-model work is `loom-port-llm`, `loom-optimize` and `loom-benchmark`, and
skill fixes follow `loom-improve`'s rules. Read the `loom` umbrella's hard rules first.

## Roles

If the host has no subagents, perform the worker steps yourself, one model at a time.
Keep the worklist, gate evidence and concise per-model conclusions on disk before
moving to the next model. The same review, publishing and GPU limits still apply;
the roles below describe responsibilities, not required agent APIs.

- **Orchestrator** (the agent running this skill): plans, keeps the worklist, dispatches subagents, reviews their
  PRs and merges the good ones. It does no porting itself, so its context holds conclusions, not kernel logs.
- **Workers** (subagents, one model or one fix each): port, optimize, publish, fix. Give each a brief that names the
  model, its Q4_K_M source, its reference (step 1), the gate set, the GPU rules and the deliverable (a published
  repo, or a PR). A worker's report is not visible to the user; the orchestrator relays what matters.

## Step 0: pick the models and see what the org has

```bash
K="${LOOM_SKILL_DIR}/scripts"
python3 "$K/rank_models.py" --top 50 --max-gb 80 -o ranked.json      # draft target list
python3 "$K/org_status.py" --org loom-fun --targets ranked.json -o status.json
```

`rank_models.py` ranks the Hub's GGUF repos (by downloads, plus the trending list) per model, by **downloads per
day since the model's first GGUF** (at most 30 days), so a model released last week isn't undercounted against
one that has been out for months. It keeps chat LLMs, groups every quantizer's repos (unsloth, bartowski,
ggml-org, ...) and variants (-GGUF, -BF16, -qat) of one model into one entry, drops user-account finetunes, and
keeps models whose plain Q4_K_M is at most `--max-gb` (80 GB leaves about 45 GB of Strix Halo's 128 GB for KV
cache and the OS). It sends the HF token from `HF_TOKEN` or `~/.cache/huggingface/token`; the anonymous API is
rate-limited.

**Review the draft by hand before acting on it.** Remove what isn't a chat model the org should host: video,
music or encoder repos the Hub mislabels (e.g. `DeepBeepMeep/MiniMax-H3`), finetunes whose card hides their base
(e.g. `schneewolflabs/B1-9B`), and `derived_from` entries that only re-tune a listed model (e.g. ThinkingCap on
Qwen3.8-27B). Keep a lab's own product built on another lab's base when it adds something (NVIDIA's Bolt-E4B on
Gemma 4: drafter, vision). One plain Q4_K_M per model; never Q8_0 or UD quants unless the user asks. Show the
list and the status counts to the user before a campaign, as a page if they'll share it.

**The target list is the top N chat LLMs by download rate whose genuine plain Q4_K_M fits the machine.**
- *Genuine* is read from the GGUF header (HTTP range read), never the filename: `general.file_type` is 15
  (MOSTLY_Q4_K_M) and the tensors are Q4_K/Q6_K. Mislabeled or re-quantized files exist, and quantizers name files in
  any case (`card_lib.quant_of` reads `q4_k_m`).
- A model with no genuine Q4_K_M never qualified, and a port that proves intractable is a failed slot. For either,
  write the reason on the model's card (publish it paused, step 2) and promote the next-ranked qualifying model, so
  the org still holds N. Keep a short ranked list of candidates ready for this.

`org_status.py` reads each org repo's own files and classifies it:

| Category | Meaning | How it's detected |
|---|---|---|
| **A** | card made by the current skill | `info.json`: `"schema": "loom-card/2"` and `"report": "generated"` |
| **B** | card made by an older skill | anything else, e.g. `"report": "attached"` (imported by `import_card.py` from an old factory run) |

A B card says nothing about the model's age: LFM3-Audio-2B was weeks old when its card was B. Only A repos are
references. For each target it assigns one action, and lists repos that duplicate a better one or match no target:

| Action | State | Next |
|---|---|---|
| `create` | no repo | step 1 |
| `update` | only a B repo, or one not built from plain Q4_K_M | step 1, from the best A reference; republish to the same repo if its checkpoint is the target's plain Q4_K_M, else a new repo |
| `fix` | A, a gate fails | step 4 |
| `remeasure` | A, a card value was measured on programs other than the repo's (`stale`, `perf.stale`) | a fresh devlab-perf job (step 3.3, step 5) |
| `investigate` | A, a metric far from its roofline (`perf.far`, judged on the card value) | step 5 |
| `sweep` | A, applicable gates, metrics or the roofline have no evidence | step 3 (gates, roofline, a devlab-perf job) |
| `done` | A, every applicable gate passes, every applicable metric measured, the roofline computed, no flag | nothing |

"Applicable" is the card generator's own rule (`card_lib.gate_applies` / `metric_applies`): vision only with a
projector, spec only with drafting, a long-document metric unless the Loom server refused that document and its
prompt is longer than the model's native context (`card_lib.over_context`; a measured value always counts), and so on. Never delete or retire a repo
yourself: list duplicates and non-targets for the user to decide. `--targets` takes `rank_models.py` output (`{"models": [...]}`) or a plain
list (entries or model ids; rank by order when absent). Each repo's `generator` is the loom-skills commit that
generated its programs: `llm_config.json` `"generator"` (build.py's stamp), else the card's recovered one
(`generator_source` says which).

## Order: references first

Group the targets by GGUF architecture and family. In each group, port the model that will serve as the
reference first (usually the smallest, so its loop is fastest), publish it as category A, then derive the others
from it: Qwen3.5-4B, then 9B, 2B and 0.8B; Qwen3.6-35B-A3B, then Ornith-1.5-35B-A3B and 122B (same `qwen35moe`
shape). Adjacent families reuse building blocks (hybrid attention, MoE routing, vision tower, chat format,
drafter), so after every publish, re-run the reference lookup (`find_reference.py rank`) for the queue. Within that order, go by action
(`fix`, `remeasure`, `investigate`, then `update` and `create` by rank, then `sweep`). New architectures with no reference (`org_status` and
the lookup both say so) are the most expensive; start them early so they run in parallel with derived ports.

## The loop

Repeat until `org_status.py` says `done` for every target.

**Every performance number on a card comes from DevLab and sits next to the roofline.** DevLab Dispatch runs the
gates (step 3), scripted ports (step 1) and the card's `devlab-perf` job (Loom with the active wait and llama.cpp on the
same runner and programs; "Performance: DevLab is the source", below). The local GPU is for development only (the
port/optimize inner loop, kernel A/B, quick checks), never for card numbers. The two are decoupled on purpose: the
local GPU never sits idle waiting for DevLab. When a model is handed to DevLab (step 3), the local GPU moves on to
the next item in the queue (a port, a fix, an optimization). DevLab results come back as gate and performance
evidence on the card and as an action in `org_status.py`; they are picked up on a later pass of the loop, not awaited.

### 1. Port and optimize (worker subagent, local GPU)

One worker per model runs `loom-port-llm` then `loom-optimize`, starting from the best category A reference
(never a B repo). A reference saves time; it never lowers the bar.

- **The reference lookup** is `loom-port-llm/find_reference.py`, which `port.sh` runs as stage 1b by default
  (`REFERENCE=off` skips it, `REFERENCE=loom-fun/REPO` picks one). It queries the org live, so a package published
  a minute ago is a reference right away; it records `llm_config.json` `"reference"` (repo, commit, reasons, what
  was taken) and seeds `draft/tune.py` with the reference's measured drafting table. An A repo built from a quant
  other than plain Q4_K_M is still used as a reference, flagged in the ranking (the repo itself is `update`).
- **Scripted DevLab ports** (no agent, no local GPU): `.github/workflows/devlab-port.yml` runs on the
  `devlab-port` label, one matrix job per entry of `.github/devlab/port.json`, each `.github/scripts/port_e2e.sh`:
  port -> qualify -> finalize with `NEEDLE_FULL=0` -> card evidence -> `publish/` (the package without weights,
  in the artifact). qualify still runs `LEVEL=quick`, its half-context needle included. Its gates and its
  performance session are the card's evidence: see the next bullet.
- **Campaign waves** (practice): put each wave on its own branch from main with only `.github/devlab/port.json`
  changed and a draft PR based on **main** (GitHub creates no pull_request runs while a PR has merge conflicts).
  Start the next wave by removing and re-adding the label through the REST API; `gh pr edit` label edits fail
  silently in this repo:
  `gh api -X DELETE repos/loom-fun/loom-skills/issues/N/labels/devlab-port`, then
  `gh api -X POST repos/loom-fun/loom-skills/issues/N/labels -f 'labels[]=devlab-port'`.
- **A DevLab-ported model**: publish it from the job's evidence (`make_info.py ... --source-kind devlab`, as
  port_e2e.sh writes it), also when the job's result is `failed gates` (step 2). The gates count, and the job's
  performance session is the card's performance (DevLab is the source): no follow-up session is needed.

- **Local GPU: one owner, one job at a time.** The local GPU is shared and small: concurrent model servers crashed
  it. Exactly one worker (the local-queue owner) runs local GPU sessions, from a
  queue file (`<repo>:<memory_bytes>` per line, a done file for results), one model loaded at a time; every other
  worker, and every kernel test, A/B and gate, runs on DevLab. CPU phases (inspection, program generation, tokenizer
  probes, card rendering) are free to run anywhere. The owner takes the lock (`flock -o /tmp/loom-gpu.lock CMD`; `-o`
  so a server CMD that stays running doesn't hold it), runs long jobs in a memory-capped scope
  (`systemd-run --user --scope -p MemoryMax=...`), and checks free memory and `pgrep -a 'loom-serve|llama-server'`
  before starting a server, stopping only its own. Follow the user's GPU instruction for the session (some forbid the
  local GPU; then use `.github/workflows/devlab-port.yml`).
- **Gates in the loop: the correctness set only.** Kernel tests, golden compare vs llama.cpp (divergences are
  near-ties), consistency, `spec` (drafting packages), agent tool loop, sampling, vision (with a projector),
  and the over-capacity 400: `LEVEL=dev` where gates.sh has it, otherwise `LEVEL=quick` without the needle.
  Needle-in-a-haystack (half and full context) and other very expensive gates belong to step 3, not the
  critical path.
- **Performance** in the loop is for development: local quiet-GPU runs (Loom and llama.cpp on the same GGUF)
  guide the optimizer but are not card numbers. The card's numbers come from the `devlab-perf` job of step 3.
- Speculative decoding stays automatic (opt-out): the optimizer picks the method and settings.

### 2. Publish the initial result

The worker publishes the package and its generated card (`loom-benchmark` "Hugging Face model card"; never
hand-written): `card/publish_package.py prepare PKG DIR --source REPO` (the GGUF repo), then `make_info.py build`
and `render_card.py DIR`, then `publish_package.py upload DIR --repo loom-fun/NAME` (`--card-only` for a card
update: README.md, info.json and REPORT.md only; `--parent-commit SHA` with the repo commit whose info.json the card
was built from, so a concurrent publish fails instead of being overwritten). Gates not yet run render as "no evidence"; that's expected and honest. The repo is now category A
and `org_status` shows it as `sweep` until step 3 fills it.

**Publish every port, done or not**, as soon as it has a package and gate evidence: failing gates, a failing
audit or perf flags don't hold it back. The card is the record of progress: a failing gate renders as fail, never
dropped or loosened, and `org_status` marks the repo `fix` (step 4). Add the card to
`.github/nightly-models.json` in the same PR, and republish as gates go green. Only `done` (below) needs every gate
passing.

**The nightly entry matches the card exactly**: `memory_bytes`, the llama.cpp build and `features` (why: the nightly
gates serve with the entry's values, so a mismatch gates a different configuration than the card claims).
`org_status` prints a `CHECK:` for a missing or differing entry. A republish that changes any of them updates the
entry in a PR. A catalog-package card (`kit: "qwen4exp"`, loom-port-llm "Catalog packages") has a `memory_bytes` above the
60 % default and an SDK pin in its `llm_config.json`: the nightly installs that SDK (`ensure_sdk.sh`) and needs a runner
with the headroom (`memcheck.sh`); refresh the pin before its `expires` (loom-setup "SDK pins").

**Memory budget** (one number for the whole card; details in `reference/lessons.md`):
- On every regeneration pass `make_info.py build --memory-bytes N` explicitly, N being build.py's printed value for
  the regenerated programs. It is not picked up from build.py, and a carried-over old value mislabels the card (#151
  now refuses it when the programs changed).
- The gates, the devlab-perf job and the nightly entry all use that same N.
- A memory-capped package (budget below context plus pool headroom) keeps a measured 2 GiB margin (build.py, #130):
  with pool equal to the context and no margin, a full-context request is refused with a 503.

**Pausing a model:** list what would be done next, one step per line in a file, and republish the card only (DIR
as in step 3.2): `make_info.py build DIR --from-info DIR/info.json --status paused --next-steps FILE`,
`render_card.py DIR`, `publish_package.py upload DIR --repo loom-fun/REPO --card-only --parent-commit $sha`. The
README then ends with a "Next steps" section. `org_status` keeps the repo's action and reports `paused: true`. To
resume, rebuild with `--status active --next-steps /dev/null`. A paused card keeps its evidence; use it also for a
model dropped from the target list (reason first in the steps).

### 3. Sweep on DevLab Dispatch: missing gates, the roofline and the performance job

DevLab is an elastic pool of Strix Halo runners; sweep many cards' gates and performance at once there, never on
the local GPU. Hand the card over and move the local GPU on to the next item.

1. The card is in `.github/nightly-models.json` (card, memory, kit, llama.cpp build; step 2). Run `nightly-gates.yml`
   (it runs on schedule, or `gh workflow run nightly-gates.yml -f models=loom-fun/REPO,... -f level=full`, or label
   a PR `nightly-gates`).
   **Wait at least 2 minutes after an upload before dispatching**: runners can still fetch the previous revision of the
   programs. If a run measured old programs, re-dispatch it.
2. When it finishes, per card, in a directory holding the repo's current `model.json`, `model.json.lock`,
   `llm_config.json` and `info.json` (re-read `info.json` from the Hub right before, at a known commit:
   `sha=$(curl -s https://huggingface.co/api/models/loom-fun/REPO/revision/main | python3 -c 'import json,sys; print(json.load(sys.stdin)["sha"])')`,
   then `curl -L -o DIR/info.json https://huggingface.co/loom-fun/REPO/resolve/$sha/info.json`):
   - `card/pull_devlab.py loom-fun/REPO --package DIR -o ev_devlab.json`: the gates, with the run, job URL and
     runner (skips jobs that measured an older revision of the package: it ingests only jobs whose `programs_sha256` equals the package's), and the spec gate's acceptance stamped with
     the job's programs: acceptance depends on the model, drafter and text, not the machine, so a sweep on the
     published programs replaces a stale `spec_acceptance` (speed stays local-only);
   - `card/make_info.py roofline --package DIR -o ev_roofline.json` (tools venv, CPU only: reads the GGUF), once
     per card or after a session changed its acceptance (a first card, with no info.json yet: add
     `--evidence ev_perf.json ev_gates.json`). A drafted row's ceiling counts the acceptance measured in the row's own
     session (perf.py, c4_steady.py), else the spec gate's, and the card says which;
   - `card/make_info.py build DIR --from-info DIR/info.json --evidence ev_devlab.json ev_roofline.json ...` (the
     repo comes from info.json, the generator commit from the checkout), `render_card.py DIR`, and
     `publish_package.py upload DIR --repo loom-fun/REPO --card-only --parent-commit $sha` (fails if another worker
     published since: re-read and rebuild).
3. A card with metrics missing or measured on other programs (`sweep`, `remeasure`): one `devlab-perf` job per card
   (required: it is the only source of card performance) (`.github/devlab/perf.json`: card, memory_bytes, kit and llamacpp from `nightly-models.json`,
   llama_spec omitted = `matched`: llama.cpp drafts exactly like the package (same method, drafter and depth; none if the
   package does not draft; see loom-benchmark "apples to apples"), an explicit `llama_spec` only overrides it (`{drafter}` = the
   card's drafter, `{hf:OWNER/REPO/FILE}` a Hub file, e.g. an MTP head the card doesn't ship); variant `{"name": "card"}`, steps `perf:card:2 perf:card:2:long c4:card llama@rocm.np1:2 llama@rocm.np1:2:long
   llamac4@rocm.nodraft` (files `perf_llamacpp-rocm.np1_nN.jsonl`, `c4_llamacpp-rocm_nN.txt`); several cards go in one experiment, one job each with its own card fields), then
   `make_info.py perf --loom-jsonl perf_card.jsonl --llama-jsonl perf_llamacpp_nN.jsonl --c4-loom c4_card.txt
   --c4-llama c4_llamacpp_nN.txt --package DIR --source-kind devlab --run ID --url JOB_URL --device JOB_DEVICE.json
   --hrx-loom JOB_HRX.json --baseline-version llamacpp-rocm/BUILD --baseline-args "$(cat llamacpp_args.txt)"
   --fetched-programs "$(cat programs_sha256.txt)"` on the job's artifact (write JOB_DEVICE.json and JOB_HRX.json with
   `card/pull_devlab.py --identity JOBDIR --device-out JOB_DEVICE.json --hrx-out JOB_HRX.json`: the runner and the SDK
   the job recorded; `none` if absent; `--source-kind devlab` is perf's default, `--source-kind local` is refused), and
   rebuild the card as above.
   **Vulkan baseline** (every card, one job each; the same workloads and `llama_spec` as the ROCm baseline): job fields
   `llamacpp_vulkan: "b12211"`, variant `{"name": "card"}`, steps `llama@vulkan.np1:2 llama@vulkan.np1:2:long llamac4@vulkan.perslot.nodraft` (Vulkan drafts like the package on 1-stream rows too)
   (add the ROCm and Loom steps to the same job for a same-runner comparison); at the card's own `memory_bytes`. Ingest:
   `make_info.py perf --backend vulkan --llama-jsonl perf_llamacpp-vulkan_nN.jsonl --c4-llama c4_llamacpp-vulkan_nN.txt
   --baseline-version b12211 --baseline-args "$(cat llamacpp_args-vulkan.txt)" --baseline-sha256 "$(cat
   llamacpp_release-vulkan.sha256)" --fetched-programs "$(cat programs_sha256.txt)" --differs "..." --package DIR
   --source-kind devlab --run ID --url JOB_URL --device none --hrx-loom none` (refused if the job fetched other
   programs than DIR's), then `make_info.py build --from-info` as above. Its numbers are another job's: compare
   engines by ratios, not across runners. KV layout (`vulkan_kv`, default auto): per-slot caches, except unified (as ROCm) for DFlash servers, where b12211 aborts on per-slot caches; the unified pool makes b12211 Vulkan attend with a dense mask (no GPU fused flash attention over K/V rows), so record that as a `--differs` line too. Every server argument that differs from the ROCm baseline, or that the Vulkan
   server could not run, goes in as `--differs "setting: reason"` (shown on the card), never changed silently. Nothing in `org_status` reads it.
4. Missing metrics come from a devlab-perf job (item 3), never from a local session.

### 4. Fix what the sweep found

A failing gate is a skill bug until proven otherwise (a model-specific workaround is the last resort). Dispatch a
worker that reproduces the failure, finds the root cause, fixes it in loom-skills under `loom-improve`'s rules
(general fix, no KPI regression, tests), and opens a PR. The orchestrator reviews it against the failure. Then
every published model the fix touches is regenerated **with the skill** by a worker (rebuild programs, re-run
the affected gates, regenerate the card); hand-patching a published package is never allowed. Merge the PR once
the regenerated models pass. Re-run `org_status.py`: anything still red goes round again.

**Gate rules:** a gate is never loosened to pass a model; the card shows the failure instead. A change to a gate rule
must come from llama.cpp's own variation, be general, and show in its PR that mutants (a deliberately wrong
Loom) still fail. Examples: the near-tie noise floor and the CPU-encoder vision recording (`loom-benchmark`). A long
metric is n/a only when its prompt exceeds the model's native GGUF context (`card_lib.over_context`).

**Regeneration safety** (a regenerated package is published only if it does not regress):
- Before publishing, A/B it against the card's own published programs on the same DevLab runner: decode, decode_32k,
  prefill 1k to 32k, streams4. Bisect main when a main build loses.
- Check that the card's generator commit is on main or in a merged PR (squash merges leave PR commits off main's
  history; `org_status` flags the rest). A card built from an unmerged branch silently loses that branch's features
  when regenerated from main (decode_32k halved this way); merge the feature first or keep the card.
- A kernel path that wins at some KV-head counts can lose at others: gate paths by shape and A/B across the
  org's shapes, not one card.

### 5. Re-measure and investigate performance

First, **re-measure** (action `remeasure`; `org_status` lists the reasons): a card value whose session measured
programs other than the repo's (`stale`: `card_lib.stale_metrics`, the session's `programs_sha256` vs the published
`program/*.loom`; the card marks them †) describes another build. Run a fresh devlab-perf job (step 3.3; Loom with the active wait and llama.cpp on the
same runner, the repo's programs) and republish the card; only then is the far flag below worth acting on.

`org_status.py` flags a category A card (action `investigate`, details under `perf.far`) when a metric is **far from
its roofline**: its Loom value is below half the efficiency Loom ports have demonstrated for that kind of metric on
this hardware (`card_lib.FAR_FRACTION` x the card's `roofline.metrics.*.efficiency`, which is `roofline.py`'s `EFF`,
or `EFF_DRAFTED` for drafted rows). Then:

1. Dispatch a worker with `loom-optimize` on the flagged metrics: a far-from-roofline metric is a
   performance problem to find and fix (ablate, compare with the roofline's gap budget, apply the lever). Profile
   first, and propose open-ended optimization to the orchestrator before starting it. Fix with a general generator
   change that lifts a whole architecture family (flash subtiles, MoE/GDN prefill kernels), never a per-model hack;
   A/B it on DevLab across the cards it touches and regenerate those through the regeneration rules above. Local
   measurements for development go to the local queue. For a
   small drafted model far from its decode roofline, the lever is the verify pass and the drafter's cost (the
   ceiling does not count the drafter); the best depth depends on the workload's acceptance, so judge it on the
   session's own acceptance, not the spec gate's.
2. The worker republishes the card with a fresh devlab-perf job (step 3.3). Move the local GPU to the next item meanwhile.
3. **Deep debugging session** when a metric is still far from its roofline after an optimization round (the card
   comes back `investigate` with the same metric after a `loom-optimize` worker's republish): the worker stops
   tuning and finds out *why* the gap stays, rather than accepting it:
   - a per-kernel profile of the flagged metric against the roofline's gap budget (which kernels, launches or
     host-side waits take the time the ceiling does not account for);
   - llama.cpp's efficiency on the same metric and machine (`loom-roofline`): a ceiling both engines are far from
     points at the model or the roofline, one only Loom is far from points at Loom;
   - the local machine's settings (power profile, CPU governor and EPP, clocks, kernel and firmware, GPU memory
     split, other load).
   The far flag is judged on the card value. Record the cause and the fix (or a skill fix under step 4) in the PR;
   a gap that turns out to be the machine, not Loom, goes into the card's evidence through a re-measured devlab-perf
   job, never by hand.

### 6. Repeat

Re-rank occasionally (new releases arrive weekly). Stop when every target is `done`, then hand the user the
duplicate and non-target lists to keep or retire.

### Far from roofline: how the threshold was set

- `FAR_FRACTION` 0.5: the category A cards that are healthy (Qwen3.8-27B, Muse-Glimmer-30B, Bolt-E4B) sit at
  0.51 or more of the demonstrated efficiency on every metric (the lowest is Bolt-E4B's 32k prefill, 0.17 of the
  roofline against 0.33 demonstrated); Flint's 1k-16k prefill sits at 0.24-0.46 of it and is flagged.
- Recalibrate it when a port moves `EFF` / `EFF_DRAFTED` (`loom-roofline`).
  `EFF_DRAFTED` was set against ceilings that counted the spec gate's acceptance; once the healthy cards'
  sessions record their own acceptance (perf.py), recompute it from those ceilings.

### Performance: DevLab is the source

Every performance number on a card comes from a `devlab-perf` job (Loom with the card's programs and llama.cpp on the
same runner). Loom used to measure well below a local session on DevLab (prefill -25 to -52 %): the DevLab runners'
SMU firmware (BIOS 1.12, SMU 0x0a640600) lowers the memory-fabric clocks (FCLK/UCLK) while the CPU is idle, and Loom
parked its CPU while the GPU worked. Loom is now served with an active wait (`serve.sh` turns `--device=amdgpu` into
`amdgpu://?completion_spin_ns=4294967295`; `LOOM_ACTIVE_WAIT=0` opts out, for A/B only), and DevLab matches or beats
the old local numbers. Local runs are for development only (the optimize/port loop, kernel A/B, quick checks), and
a Loom number measured without the active wait is not comparable with a card's.

## Orchestrating many workers

Rules; the reasons and details are in `reference/lessons.md`.
- Keep a handoff file (state, active workers, open PRs, next actions) and a status page; refresh `org_status` and the
  page after every change. Sessions restart: everything must be resumable from disk.
- Every PR gets an independent review before merge (DRY, general, no regression, no vendored package contents); the
  orchestrator merges, workers don't.
- The shared checkout stays on `main`; branches live in worktrees.
- Big files (GGUFs, tables, logs) never go in tmpfs (`/tmp` may be RAM).
- Workers wait on runs with background waits and end their turn, not foreground sleeps.
- Every card passes the full gate set, not just golden: the sweep keeps finding correctness bugs golden misses
  (tokenizer pre-tokenizer quirks, batch-dependent prefill numerics, kernel paths that depend on KV heads).

## Done

A model is done when its repo is category A, built from the target's plain Q4_K_M, every applicable gate passes
(including needle and full-context, from the sweep), every applicable metric is measured in a devlab-perf job
(Loom and llama.cpp, the published programs), the card carries its roofline, no metric's card value is far from it,
and the card was regenerated
after the last skill fix that touched it. The org is done when every target is
done and the user has decided on the rest.
