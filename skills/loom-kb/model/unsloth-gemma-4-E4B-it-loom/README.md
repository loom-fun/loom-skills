# Gemma 4 E4B

`memory.kv.compact_gemma4_e4b` is an experimental, default-off text-only cache layout. No scope rule enables it. It keeps the four unique global K/V pairs paged and stores the twenty local pairs in private SDK recurrent slots with 2048 positions and 1024 bytes per local K or V position. At a 65536-position pool, cache data occupies 1,157,627,904 bytes (1.078125 GiB), versus 6 GiB in the uniform layout. This is a source allocation estimate, not measured total RAM.

The first prototype requires the E4B Q4_K_M configuration, `target.rdna4_twins=false`, `--draft none`, `--rows 1`, prefill at most 1024, and an explicit context of 1024..65536 in multiples of 1024. The pool must equal context; the SDK's fixed pool uses that context. Remove the image component from the input config for a text-only build. Set both choices in that config's `choices` map, or use `GEMMA4_COMPACT_KV=1 LOOM_RDNA4=0` for an explicitly dirty experiment.

The emitted preset sets `max_sessions=1` and zero session cache, prefix cache, cache target bytes, and checkpoint capacity. Prepare and storage (including resize) reject extra rows, cache pins, larger epochs, and contexts above 65536. Draft and image support are excluded. Absolute RoPE positions and F16 cache values are preserved. Prefix/fork support would require an ordered retained-history copy from reader slot to writer slot; it is not implemented here.

A 512-position ring is insufficient: prefill writes all K/V before earlier queries read their windows. A 1024-token epoch requires 1535 semantic positions, plus up to 15 masked historical lanes in aligned decode loads. The 2048-position ring preserves those loads as well. All emitted local arena views must trace to an audited compact address plus at most one V-plane and 15 contiguous positions; unknown recipes fail the build.

The CPU test `tests/test_compact_kv.py` can interpret the actual emitted address functions with `--legacy .../llm.loom --candidate .../llm.loom --output result.json`. It checks shuffled pages, boundary positions, all owner/head layouts, chunk write overlap, synthetic F16/f64 attention, and deliberate bad rings/strides/forks. The unchanged arithmetic and launches are also compared. This does not establish GPU kernel/model numerical correctness or memory/speed gains. The checkpoint's actual byte identity must still be verified by the experiment runner; geometry and filename checks are not a checkpoint hash.
